## 4.1 从零开始设计计算机

### 4.1.1 复杂系统都是迭代出来的 ★★

课件开场的例子：

- Intel Raptor Lake S（8P + 16E），2022 年 9 月发布——你的笔记本 CPU 有上百条特性；
- x86 从 1978 年的 80 条指令，发展到 2015 年的 3600 条；
- Windows 的窗口重叠、双击运行、Ctrl+C/V，都是一个个版本叠出来的。

结论：**没有哪个复杂系统是“设计”出来的，都是“长”出来的**。这直接决定了 AM 的设计哲学：先完成，后完美。

### 4.1.2 三个理论坐标 ★★

| 年份 | 东西 | 要点 |
| :---: | :--- | :--- |
| 1936 | 图灵机 | 状态转移表 = 指令；`<input, output, move, next state>`；跳到未定义状态即停机 |
| 1936 | 通用图灵机（UTM） | **UTM = 计算机，T = 程序**：输入任意图灵机，执行结果与它等价 |
| 1945 | 冯·诺依曼计算机 | ENIAC；1948 年改进版成为**第一台存储程序**通用电子计算机 |

> [!important] 重点
> UTM 的意义：**“在 NEMU 里执行程序”和“UTM 执行 T”是同一件事**。你今天写的模拟器，就是图灵 1936 年那个构造的实现。

存储程序的意义：内存**可写**，所以“一个程序可以读入另一个程序并执行”——这是编译器、shell、操作系统存在的物理基础（`ls` 就是一个被读入并执行的程序）。

### 4.1.3 硬件机制的演进阶梯 ★★★

| 机制 | 带来什么 | 系统形态 |
| :--- | :--- | :--- |
| 自陷 / 异常 | 一个程序能停下来，交回控制权 | 批处理系统 |
| 中断 + 虚拟内存 | 程序能被“打断”和“隔离” | 分时多任务 |
| 多处理器 | 真正同时执行 | 多处理器系统 |

这条阶梯就是 AM 的模块划分依据（见 4.3）。

## 4.2 两个问题，两个诀窍

### 4.2.1 问题 ★★★

1. **硬件细节不一致**：串口地址不同、型号不同。直接在这些机制上编程，程序里就全是硬件细节。
2. **自制处理器也在迭代**：你现在写的处理器跑不了操作系统，程序的执行需要运行时环境支持。

### 4.2.2 诀窍 ★★★

1. **抽象**：引入一个新层，把机制的功能抽象成 **API**。程序只调 API，不碰细节。这套 API 就叫 **Abstract Machine（AM）**。
2. **模块化**：把机制分模块，按需组合。

| 模块 | 全称 | 提供什么 |
| :--- | :--- | :--- |
| **TRM** | Turing Machine | 计算的最基本支持 |
| **IOE** | I/O Extension | 输入输出 |
| **CTE** | ConText Extension | 上下文（中断/异常） |
| **VME** | Virtual Memory Extension | 虚拟存储 |
| **MPE** | Multi-Processor Extension | 多处理器 |

> [!important] 重点
> AM 不是“又一层抽象”，而是**按计算机发展史切分的抽象**。每个模块对应一个历史阶段的需求，所以它既好讲（有故事线）又好用（可裁剪）。

## 4.3 五个模块与它们的 API

### 4.3.1 TRM：最小的裸机运行时环境 ★★★

一个“只会计算”的程序需要什么？

| 需求 | 提供物 |
| :--- | :--- |
| 能执行指令的环境 | 模型机（NEMU / 你的处理器） |
| 能自由计算的内存 | 堆区 |
| 程序入口 | `main(const char *args)` |
| 退出方式 | `halt()` |
| 打印字符 | `putch()` |

有了这五个，程序就能打印 Hello World 了。

> [!important] 重点
> 还记得“只支持两条 RISC-V 指令的自制运行时环境”吗？**它就是 TRM 的简化版**。AM 不是新东西，是你已经写过的东西的完整版。

### 4.3.2 IOE：输入输出 ★★

- `ioe_read()` / `ioe_write()`；
- 一组约定的抽象设备：时钟、键盘、2D GPU（可选：串口、声卡、磁盘、网卡）。

有了 IOE，你就得到了一个**冯·诺依曼计算机系统**——课件展示的是在 x86-nemu 上跑超级玛丽。

### 4.3.3 CTE：上下文管理 ★★

- 上下文保存/恢复；
- 事件处理回调；
- `kcontext()` 创建内核上下文；
- `yield()` 自陷；
- `ienabled()` / `iset()` 中断查询/设置。

有了 CTE，就得到**批处理系统**（小霸王 100 in 1、仙剑），甚至**分时多线程系统**（类似 RT-Thread）。

### 4.3.4 VME 与 MPE ★

| 模块 | API | 得到什么 |
| :--- | :--- | :--- |
| VME | `protect()` 创建地址空间、`map()` 建立 va→pa 映射、`ucontext()` 创建用户上下文 | 分时多任务、现代 OS |
| MPE | `cpu_count()`、`cpu_current()`、`atomic_xchg()` | 多处理器系统 |

### 4.3.5 KISS 原则与取舍 ★★★

AM 的设计原则是 **KISS：用最少的 API 实现现代计算机系统软件**。

| 模块 | 取舍 |
| :--- | :--- |
| TRM | 最小的裸机运行时环境 |
| IOE | 只提供读写接口和少量抽象设备 |
| CTE | 统一但相对低效的中断异常处理 |
| VME | 页式虚存管理的**基本机制** |
| MPE | 简化的并发模型和原子操作 |

**失去的**：不连续/热插拔内存、PCIe 等现代设备、快速中断、页表的 A/D 位、其他原子操作。
**得到的**：适合教学的简洁概念和实现。

> [!note] 考点
> “AM 是完整操作系统吗？”——不是。它刻意**只保留基本机制**，把策略留给上层。这是“机制与策略分离”的教科书式示范。

## 4.4 AM 的意义（三点）

### 4.4.1 按计算机发展史模块化 ★★★

从需求出发，反推“计算机该有什么”：

| 程序想要 | 需要什么机器 | 模块 | 对应课程 |
| :--- | :--- | :---: | :--- |
| （高效地）计算 | 支持指令集的图灵机 | TRM（必选） | 你现在做的 |
| 输入输出 | 冯·诺依曼机 | IOE | B 阶段、南大数电实验 |
| 依次运行多个程序 | 批处理系统 | CTE | B 阶段 |
| 并发运行多个程序 | 分时多任务 | VME | A 阶段、南大 PA |
| 并行运行多个程序 | 多处理器系统 | MPE | 南大 oslab |

> [!important] 重点
> 这张表就是“为什么 NEMU 要支持 `putch`、为什么要做 `yield`”的答案：**每一个 API 背后，都是一个历史阶段的需求**。理解了需求，你就知道该实现什么、为什么实现它。

### 4.4.2 裸机运行时环境：软硬协同的接缝 ★★★

```
(在 CPU 中) 实现功能 → (在 AM 中) 提供运行时环境 → (在应用层) 运行程序
(在 CPU 中) 实现更强大的功能 → (在 AM 中) 提供更丰富的运行时环境 → (在应用层) 运行更复杂的程序
```

这就是“一生一芯”的主线：**你做的每一件事，都在这个三角里找一个位置。**

### 4.4.3 抽象：打通所有课程实验的关键 ★★★

- 在 AM 上写程序 → 可以跑在**任何**支持 AM 的机器上：cputest、coremark、microbench、litenes、FCEUX，甚至 OS。
- 为机器实现 AM → 可以运行**任何**基于 AM 的程序：x86-nemu、mips32-qemu、riscv32-npc、riscv64-xiangshan、Linux native。

真实案例：国科大系统结构实验用 LoongArch，有同学想接入“一生一芯”——**实现一个 LoongArch 的 AM，就能跑仙剑**。

### 4.4.4 抽象的三个附带好处 ★★

1. **裸机程序更容易开发**：几乎和 hosted 环境一样，不用关心硬件细节。
2. **操作系统更容易理解**：传统 OS 课要讲 x86 的保护模式、GDT、IDT、TSS、CR3、页表……有了 AM，**操作系统就是一个从 `main()` 开始执行的 C 程序**。
3. **全系统更容易调试**：先让 Linux native 的实现正确，再搬到硬件上；还可以做 trace、model checking、形式验证。

> [!important] 重点
> 第 2 条是本讲最“爽”的结论：AM 把“启动”这件事从几百页手册变成了一个 `main()` 函数。

## 4.5 AM 代码导读

### 4.5.1 编译链接与启动流程 ★★★

AM 的执行链条非常短：

```
链接脚本（linker script）决定入口和内存布局
   ↓
_start：设置栈指针 sp，跳转到 _trm_init()
   ↓
_trm_init()：调用 main(args)
   ↓
main() 返回后调用 halt(ret)
```

- **链接脚本**（`linker.ld`）指示程序入口（`ENTRY(_start)`）和内存布局（text/data/bss/stack 各在哪）；
- `_start` 是汇编，负责把 `sp` 指向栈顶（`_stack_top`），然后 `call _trm_init`；
- `_trm_init` 是 C 函数，把控制权交给 `main`；
- `halt()` 负责“停机”，在 NEMU 上通常就是一条 `ebreak`（触发 GOOD TRAP）。

> [!note] 考点
> “为什么裸机程序的第一条指令不是 `main`？”——因为 C 函数的运行需要栈，而**栈指针还没设置**。`_start` 的存在就是为了在没有运行时环境的情况下，手工把机器摆到“可以调用 C 函数”的状态。

### 4.5.2 klib：机器无关的运行时库 ★★

AM 还提供了 `klib`：`printf`、`sprintf`、`strcpy`、`memcpy`、`memset`、`atoi`、`rand` 等常用函数。

- 它们**不依赖 libc**（裸机没有 libc）；
- 用 `putch()` 作为输出出口，所以 `printf` 在 NEMU 上能工作；
- 这是“机器无关层”，换架构不用改。

> [!important] 重点
> `klib` 的位置很关键：它在 **AM 之上、程序之下**。所以 `printf` 是“AM 的一部分”，不是“操作系统的系统调用”。

## 4.6 AM 的八卦：一段教学史（了解即可）

### 4.6.1 从“各做各的”到“搞个大的” ★

南京大学的实验课是逐年长出来的：

| 年份 | 事件 |
| :---: | :--- |
| 2008 | 06 级学长设计第一版**组成原理**实验 |
| 2010 | 07 级学长设计第一版**操作系统**实验 |
| 2012 | 08 级学长设计第一版**编译原理**实验 |
| 2014 | 10 级学长设计第一版**系统基础**实验 |

2017 年 1 月，和 jyy 讨论：“该有的都有了，要不搞个大的？”——自己写 CPU，上面跑自制 OS，再跑自制编译器编出的程序，这个程序可以是 NEMU，于是又能跑自制 OS……（递归了）

两个最大挑战：

1. **每个实验的 ISA 不同**（组成原理/编译原理用 MIPS，OS/系统基础用 x86）；
2. **全系统有 bug 怎么调试**。

### 4.6.2 AM 的诞生 ★

- 2017 年 3 月 10 日，jyy 在计算机系统综合实验课上介绍 AM 的初步想法：**用抽象层把 ISA 和 OS 解耦**；
- 3 月 17 日，介绍第一版 API。

同年提出三件有影响力的教学成果：AM、NEMU 加入 DiffTest、第一版 Project-N 生态。

| Project-N 组件 | 说明 |
| :--- | :--- |
| Navy-apps | 应用程序集 |
| NCC | NJU C Compiler |
| Newlib | 嵌入式 C 库（移植） |
| Nanos / Nanos-lite | NanJU OS 及其简化版 |
| Nexus-AM（旧名） | 抽象计算机，裸机运行时环境 |
| NEMU | NJU EMUlator，全系统模拟器 |
| NPC | NJU Personal Computer，SoC |
| NOOP | NJU Out-of-Order Processor |

> [!important] 重点
> 这套东西后来影响了“一生一芯”（1/2/3）、香山（1/2）、龙芯杯（2）的流程。也就是说：**你现在做的实验流程，是一套被验证过、被多所学校复用过的东西**。

### 4.6.3 一些很酷的想法 ★

- 给 RT-Thread 加一个用 AM 实现的 BSP（已实现，进入 B 阶段）；
- 把 xv6 移植到 AM（进行中）；
- 给 Linux 加一个用 AM 实现的 `arch`（不完整的 CPU 也许能“部分”跑 Linux）；
- 把 Verilator 编译的香山移植到 AM，在 NPC 上仿真香山。

## 4.7 本讲小结与自测

### 4.7.1 小结 ★★★

- 复杂系统靠迭代；计算机的能力是一层层加上去的。
- 两个问题（硬件细节不一致、自制处理器不完整）→ 两个诀窍（抽象、模块化）。
- AM 五模块：TRM（计算）、IOE（IO）、CTE（上下文）、VME（虚存）、MPE（多处理器）。
- KISS：最少的 API；失去现代特性，得到教学上的简洁。
- 意义三点：按历史模块化、裸机运行时环境、抽象打通所有实验。
- 启动链：链接脚本 → `_start`（设 `sp`）→ `_trm_init` → `main` → `halt`。

### 4.7.2 自测

1. 用一句话解释 UTM 和“在 NEMU 里跑程序”的对应关系。
2. TRM 只提供五个东西，分别是什么？为什么“打印字符”也算最基本的需求？
3. 为什么 `_start` 必须是汇编，不能直接是 `main`？
4. AM 的“模块化”是按什么维度切的？举出每个模块对应的系统形态。
5. KISS 原则让 AM 失去了哪些能力？为什么这些取舍在教学场景下是合理的？
6. `printf` 在 AM 里属于哪一层？它最终调用了什么？

# 附录 B 自测题答案要点

## B.1 第 4 讲

1. **UTM = 计算机，T = 程序**；NEMU 就是 UTM 的一个实现，被模拟的程序就是 T。
2. **TRM 五件套**：模型机、堆区、`main(args)`、`halt()`、`putch()`；输出是程序最自然的需求（图灵机也要输出 0/1）。
3. **`_start` 必须是汇编**：C 函数需要栈，而 `sp` 还没设置；`_start` 负责设 `sp` 再 `call`。
4. **按计算机发展史切分**：TRM→图灵机、IOE→冯·诺依曼机、CTE→批处理、VME→分时、MPE→多处理器。
5. **失去**：不连续/热插拔内存、PCIe、快速中断、页表 A/D 位、更多原子操作；**合理**因为教学要的是“最小可用机制”，策略留给上层。
6. **`printf` 在 klib**（AM 的机器无关库），最终通过 `putch()` 输出，`putch` 由具体平台的 TRM 实现。

# 附录 C 术语表

| 术语 | 含义 |
| :--- | :--- |
| ISA | 指令集体系结构，软件与硬件的接口 |
| ABI | 应用二进制接口，规定调用约定、数据布局等 |
| AM | Abstract Machine，按功能模块化的裸机运行时环境 |
| TRM / IOE / CTE / VME / MPE | AM 的五个模块 |
| NEMU | NJU EMUlator，全系统模拟器 |
| YEMU | 教学用的极简模拟器（NEMU 的前身） |
| DiffTest | 差分测试：用参考实现对照被测实现 |
| UB | 未定义行为，编译器可假设其不发生 |
| prologue / epilogue | 函数准备/结束阶段 |
| caller-saved / callee-saved | 调用者保存 / 被调用者保存 |
