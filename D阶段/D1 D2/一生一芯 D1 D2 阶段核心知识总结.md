* # 一生一芯 D1 & D2 阶段核心知识总结

  这份总结融合了 D1 阶段（C语言底层与编译流程）和 D2 阶段（表达式求值、调试器与自动化测试）的核心难点。它不是流水账，而是你未来查阅的“底层开发避坑指南”。

  # 🟢 D1 阶段：C语言底层、编译流程与程序生命周期

  ## 一、 编译的四大阶段与工具链
  从源代码到可执行文件，必须经历四个阶段，这正是 `gcc`/`clang` 大显身手的地方：
  1.  **预处理（`-E`）**：处理 `#include`、`#define`，展开宏，去掉注释。
  2.  **编译（`-S`）**：将 C 代码翻译成**汇编代码**（`.s` 文件），进行语法和语义分析。
  3.  **汇编（`-c`）**：将汇编代码翻译成**机器码**（`.o` 目标文件）。
  4.  **链接**：将多个 `.o` 文件与系统库合并，生成最终的**可执行文件**。
  *   **工具**：`gcc` 与 `clang` 在前端行为上几乎一致（`clang` 报错更友好）；`objdump -d` 可将机器码**反汇编**。

  ## 二、 预处理与宏（Preprocessing）
  *   **`-I` 参数**：编译时，用 `-I <dir>` 告诉编译器优先去哪个目录找头文件。
  *   **宏展开**：
      *   `#` 操作符：将参数转成字符串（Stringizing）。
      *   `##` 操作符：拼接两个 Token（Token Pasting）。
  *   **条件编译**：`#ifdef`、`#ifndef` 等。这是跨平台代码（如区分 x86 和 RISC-V）隔离差异的核心手段。

  ## 三、 C语言标准里的“三大恶人”
  写底层代码，必须敬畏标准，否则会引发极其难查的 Bug：
  1.  **未定义行为（Undefined Behavior, UB）**：如数组越界、空指针解引用。标准规定“一切皆有可能”，编译器甚至可能直接删掉这段代码。
  2.  **未指定行为（Unspecified Behavior）**：如函数参数的求值顺序（`f(i++, i++)`），不同编译器（甚至同编译器不同版本）结果不同。
  3.  **实现定义行为（Implementation-defined Behavior）**：如 `int` 到底占几个字节。标准要求编译器自己定并写入文档，所以跨平台移植代码时，**永远不要相信基本类型的大小，必须用 `<stdint.h>` 里的 `uint32_t` 等**。
  *   **顺序点（Sequence Point）**：C标准规定两个顺序点之间，同一个变量只能被修改一次（如 `;` 就是一个顺序点），否则就是未定义行为。

  ## 四、 `volatile` 关键字
  *   告诉编译器：“这个变量可能会被硬件或中断意外修改，**不要自作聪明去优化它**”。每次使用都必须从内存真实读取。在写设备驱动（如映射硬件寄存器）时必用。

  ## 五、 ABI（应用程序二进制接口）
  *   **软硬件的契约**：API 是给程序员看的，**ABI 是给编译器（生成机器码）和硬件（CPU执行）看的**。
  *   它规定了：数据类型的大小（如 RISC-V 的 `int` 是 32位）、寄存器怎么传参（如 RISC-V 用 `a0-a7` 传参，返回值放 `a0`）、栈帧的结构等。
  *   **核心关联**：未来你写的 NPC（硬件）必须严格遵守 ABI，否则编译器生成的代码在你的 CPU 上就会跑出乱码。

  ## 六、 程序的生命周期（极其重要）
  *   **入口点**：程序并非直接从 `main()` 开始执行。Linux 加载器加载程序后，第一条指令在 `_start`（由 `crt0.o` 提供）。`_start` 准备好栈、提取参数，才会 `call main`。
  *   **退出**：`main` 返回后，会调用 `exit` 刷新缓冲区，最后通过系统调用（如 RISC-V 的 `ecall`）把控制权交还操作系统。

  # 🔵 D2 阶段：表达式求值、监视点与自动化测试

  ## 一、 词法分析（Tokenizer / 字符串切分）

  ### 1. 枚举设计与架构解耦
  *   **`TK_` 枚举**：自定义类型（如 `TK_NUM`, `TK_REG`）必须从 `256` 开始，以避开 0-255 的 ASCII 码冲突。
  *   **架构解耦**：`sdb.c`（命令行入口）只负责路由；`expr.c` 负责解析求值；测试逻辑独立成文件。

  ### 2. 正则匹配的致命陷阱
  *   **`regexec` 的“跳跃匹配”**：正则引擎默认会在字符串后面寻找匹配项。必须加 `&& pmatch.rm_so == 0`，强制匹配**必须从当前指针所指字符开始**。
  *   **C 控制流陷阱（Match 后必须 Break）**：`for` 循环遍历规则时，匹配成功必须 `break`。否则循环结束 `i == NR_REGEX`，会被误判为“未找到”而 `return false`。
  *   **边界与截断**：`char str[32]` 最多装 31 个字符 + 1 个 `\0`。判断必须写 `>= 32`。`strncpy` 不会自动补 `\0`，必须手动加上，防止打印出内存垃圾。

  ## 二、 语法分析与递归下降求值

  ### 1. `p` 和 `q` 的物理意义
  *   `p` 和 `q` 是 Token 数组的**闭区间下标**。
  *   **剥括号**：`eval(p + 1, q - 1)`。
  *   **切分**：主运算符在 `op`，则左边 `eval(p, op - 1)`，右边 `eval(op + 1, q)`。

  ### 2. 核心逻辑：`eval` 的三大关卡
  1.  **死胡同**：`p == q`，直接返回该 Token 的数值（递归出口）。
  2.  **脱衣服**：`check_parentheses(p, q)` 返回 `true`，剥掉括号继续递归。
      *   *注意*：如果返回 `false`（如 `1+2`），程序不会崩溃，而是滑入 `else` 分支去找主运算符。
  3.  **找主运算符砍一刀**：寻找优先级最低、且不在括号内的运算符。

  ### 3. 找主运算符（`find_main_op`）法则
  *   **从右往左扫**：因为 C 语言同级运算符**左结合**（如 `8-3-2` 等价于 `(8-3)-2`），从右往左最先碰到的 `+` 或 `-` 才是最后执行的。
  *   **括号保护罩**：用 `count` 变量。遇 `)` 加 1，遇 `(` 减 1。只有 `count == 0` 碰到的运算符才有效。
  *   **优先级策略**：先记下乘除号，一旦遇到加减号（优先级更低），直接丢弃备选，锁定并返回加减号。

  ### 4. 数字转换陷阱（千万别用 `atoi`）
  *   **为什么不用 `atoi`**：无法处理十六进制（遇 `0x` 返回 0），出错也返回 0，大数（如 `0xFFFFFFFF`）会溢出。
  *   **标准解法**：使用 `strtol` 或 `strtoul`，支持指定进制，并能通过 `endptr` 校验是否完全解析。

  ## 三、 监视点（Watchpoint）与底层硬件思维

  ### 1. 监视点的本质
  *   **条件报警器**：只要表达式（如 `$pc` 或内存地址）的值发生变化，NEMU 就立刻暂停。它模拟了硬件里的“数据断点”。
  *   **软件实现**：CPU 每跑一步，就重新算一遍表达式进行对比。

  ### 2. 工业级重构：对象池与宏开关
  *   **对象池（Pool）取代 `malloc`**：用固定大小的 `wp_pool[32]` 数组和两个链表（`head` 和 `free_`）管理。
      *   **优势**：像硬件一样，固定坑位。分配释放极快（O(1)），绝不产生内存碎片或泄漏。
  *   **零开销性能优化**：
      *   **`IFDEF(CONFIG_WATCHPOINT, ...)`**：编译阶段若关闭功能，直接把代码当垃圾删掉，二进制里没有任何指令。
      *   **`while (head != NULL)`**：即使开启，没设监视点时也只是一次极快的空指针判断，绝不执行耗时的 `expr()`。

  ### 3. 断点的本质（思考题总结）
  *   调试器（如 GDB）的断点并非纯软件模拟，而是“偷梁换柱”：把原指令替换为陷阱指令（如 RISC-V 的 `ebreak`），触发中断后再换回。

  ## 四、 自动化测试与差分测试（DiffTest）

  ### 1. 核心思想
  *   利用宿主机 GCC 作为**标准答案（参考模型）**。
  *   流程：生成器生成表达式 -> 塞给 C 代码由 GCC 算出结果 -> 存入 `input` -> NEMU 读出计算 -> 对比结果。

  ### 2. 生成器的难点（除零检测）
  *   静态扫描不管用（防不住 `10 / (2-2)`）。最可靠的是让 GCC 实际运行。
  *   若触发 `SIGFPE`（浮点异常），说明用例非法，直接丢弃。NEMU 中通过 `ret != 1` 过滤。

  ### 3. 测试策略与性能
  *   **循序渐进**：先用两位数跑通逻辑，再加 `0`、`0xFFFFFFFF` 等边界值。
  *   **性能陷阱**：大量 `Log` 会严重拖慢性能（涉及 I/O），自动化测试时要关闭 `Trace` 或注释掉 `Log`。

  ## 五、 调试哲学与工具
  *   **Fault -> Error -> Failure**：尽早拦截。写错代码不一定会崩溃，跑飞时现场往往已破坏。
  *   **编译期防御**：`-Wall -Werror` 把警告当错误，扼杀在摇篮。
  *   **底层检测神盾（Sanitizer）**：利用“影子内存”机制，把越界/释放的内存标记为“毒药”，访问立刻报错。
  *   **GDB**：配合 `starti` 可查看 `_start` 入口，是未来排查 NEMU 或 RTL 硬件 bug 的终极武器。
