# “一生一芯” NEMU 调试基建与 DiffTest 协同架构总结

在完成从 minirv 到 RV32E 的指令集升级过程中，你的 NPC 已经从“裸车”升级成了拥有 SDB、Trace 和 DiffTest 的工业级仿真系统。以下是这一阶段的核心知识点与工程避坑指南。

---

## 模块一：SDB 调试器的设计哲学与实现

### 1. 表驱动法（命令注册机制）
*   **痛点**：如果用 `if-else` 处理所有命令（如 `si`, `info`, `c`, `q`），代码会变成又臭又长的屎山，且极难扩展。
*   **解决方案**：使用**函数指针 + 结构体数组**（命令表）。
    *   定义一个命令结构体：`{ 命令名, 描述, 处理函数指针 }`。
    *   通过 `add_sdb_cmd` 将命令注册到全局数组 `cmd_table` 中。
    *   **好处**：主循环只需遍历数组比对字符串，找到后调用对应的函数指针。未来增加新命令时，不需要修改主循环，只需写个新函数并注册即可（对修改封闭，对扩展开放）。

### 2. 输入解析利器：`readline` 与 `strtok`
*   **`readline`**：用于替代简陋的 `scanf`。它提供了类似 Linux Shell 的体验，支持**行内编辑、光标移动、上下键查看历史**。它返回的字符串是内部动态分配的，用完必须 `free`。
*   **`strtok(NULL, "")` 的魔法**：在解析命令时，`strtok(str, " ")` 取出命令名（如 `x`），而 `strtok(NULL, "")` 使用空字符串作为分隔符，它会**将剩余的所有参数（如 `10 0x80000000`）原封不动地打包返回**，非常适合作为参数传递给具体的处理函数。

### 3. 信号处理：为什么拦截 `Ctrl-C`？
*   **默认行为**：在普通程序中，`Ctrl-C` 发送 `SIGINT` 信号，操作系统会直接杀死进程。
*   **调试器需求**：在调试硬件时，进程被杀死意味着内存和寄存器状态全部丢失，无法排查 Bug。因此必须拦截。
*   **安全准则（极重要）**：
    *   信号处理函数 `on_sigint` 内部**绝对不能**调用 `printf` 或 `malloc`，因为此时主程序可能正在占用锁，会导致死锁。
    *   **正确做法**：使用 `volatile sig_atomic_t` 声明全局标志位。处理函数只负责把标志位置 1，主循环检测到标志位后，再安全地执行暂停逻辑。

## 模块二：硬件仿真环境的时序与总线模型

### 1. 为什么需要 `BusReq` 结构体快照？
*   **时序博弈**：多周期 CPU 的请求信号（`reqValid`、`addr`）是组合逻辑输出。当 `top.clock = 0`（低电平）时，信号稳定；一旦 `top.clock = 1`（高电平）到来，硬件状态机翻转，`reqValid` 可能瞬间拉低，`addr` 可能切到下一条指令。
*   **快照的意义**：必须趁着 `clk=0` 时，用 `sample_request()` 把当前总线上的请求（是否读、地址、数据、掩码）**像拍照一样全部抓拍进 `BusReq` 结构体**。后续的响应拍（`drive_response`）只看这个快照，哪怕硬件此时天翻地覆，也不会导致丢请求或错位。

### 2. RTL 调试端口的时序对齐
*   **教训**：`debug_inst` 和 `debug_inst_pc` 必须在 **S_IF2（译码拍）锁存**，而不是在提交拍（retire）直接取指。
*   **原因**：retire 脉冲比提交晚一拍。如果到 retire 才去读总线，总线早就去预取下一条指令了，会导致反汇编彻底错位。

## 模块三：DiffTest 的核心原理与黑白魔法

### 1. 核心概念扫盲
*   **DUT (Device Under Test)**：待测设备。即你用 RTL 写的 NPC（通过 Verilator 生成的 C++ 模型）。
*   **REF (Reference Model)**：参考模型。即你写的 NEMU，它是绝对正确的“标准答案”。
*   **API (应用编程接口)**：也就是“菜单”，定义了软件怎么互相调用（如 `difftest_exec`）。
*   **ABI (应用二进制接口)**：也就是“物理插头”，规定了数据在内存里的布局规则。`memcpy` 能正常工作的前提是，NPC 的状态结构体和 NEMU 的状态结构体必须遵守相同的 ABI（字段顺序和大小完全一致）。

### 2. 共享库（`.so`）：没有 `main` 的幽灵
*   **可执行文件 vs 共享库**：可执行文件有 `main`，能自己运行；共享库只是“零件”，不能独立运行。
*   **动态加载（`dlopen` & `dlsym`）**：NPC 通过 `dlopen` 把 NEMU 加载进内存，通过 `dlsym` 找到 NEMU 暴露出的接口地址。由于没有入口点，必须手动调用 `difftest_init` 来唤醒 NEMU 的日志系统和内存分配。
*   **驱动机制**：NEMU 不是自己跑的，是 NPC 每提交一条指令，就通过函数指针调用 `p_exec(1)`，**“扯着”** NEMU 往前走一步。

### 3. `memcpy` 的暴力美学
*   **本质**：只认字节，不认类型。不管你是整数、浮点数还是巨大的结构体，它一律按字节逐个搬运（底层库甚至用 SIMD 指令一次搬 32 字节）。
*   **应用**：`difftest_regcpy` 直接通过 `memcpy` 将整个 CPU 状态结构体镜像给另一方，速度极快。
*   **避坑**：绝对不能用 `memcpy` 处理内存重叠（Overlap）的区域，否则会覆盖未读数据，这种情况必须用 `memmove`。

### 4. MMIO “作弊”机制
*   **痛点**：NPC 硬件可以访问串口读入字符，但 NEMU 纯软件模拟没有真实外设，会导致比对失败。
*   **解决**：当总线检测到访问的是 MMIO 时，调用 `nemu_ref_mark_mmio()` 打标记。比对时，`nemu_ref_step` 发现标记为真，**不执行 NEMU 的指令**，直接将 DUT 的状态强行同步给 NEMU。让双方“和解”。

## 模块四：从 C 代码到硬件的全景视角

###  C 程序是怎么跑起来的？
1.  **AM (Abstract Machine)** 类似游戏卡带的“配件包”。`make ARCH=xxx` 决定了打包哪个底层（native 调 Linux 系统调用，npc 调 UART MMIO）。
2.  **GCC 编译器** 根据 `-march` 和 ISA 规范，把 C 代码翻译成二进制机器码，加载进 `pmem`。
3.  **Verilator** 模拟时钟翻转，PC 指向 `0x80000000` 开始取指。
4.  **执行**：取指 → 译码 → ALU 执行 → 访存（触发 `BusReq`） → 写回。遇到 `sw` 写 UART，C++ 打印字符；遇到 `ebreak`，停机。
