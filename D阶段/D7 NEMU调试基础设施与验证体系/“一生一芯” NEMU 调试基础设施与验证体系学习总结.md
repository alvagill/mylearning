# “一生一芯” NEMU 调试基础设施与验证体系学习总结

在 NEMU 模拟器的开发过程中，从“让程序跑起来”到“保证程序不跑飞”，离不开一套强大的调试与验证基础设施。这份总结将系统梳理这些底层的工具链原理、测试方法论以及工程避坑指南。

---

## 模块一：三大追踪利器（Trace）底层原理解析

### 1. 指令追踪（itrace）与 环形缓冲区（iringbuf）
*   **itrace 的局限**：如果把所有指令都打出来，终端会被瞬间刷爆。程序崩溃时，你真正关心的只有**崩溃前最后执行的十几条指令**。
*   **iringbuf（黑匣子）的实现精髓**：
    *   **数据结构**：**环形缓冲区**。固定大小（如 16），用取模运算 `% IRINGBUF_SIZE` 控制指针绕圈。
    *   **覆盖逻辑**：当缓冲区存满后，新的指令会覆盖最旧的指令。`head` 永远指向下一个将被写入的空位。
    *   **核心公式**：`start = (head - count + SIZE) % SIZE`。这行代码用于找到当前最旧指令的索引，确保打印时按**时间先后顺序**输出，即使物理上它已经绕圈了。
    *   **安全拷贝**：字符串的拷贝（`strncpy`）非常讲究。绝不能直接 `=`，必须用 `strncpy` 并手动补 `\0`，防止溢出；或者用 `snprintf` 一步到位。

### 2. 内存追踪（mtrace）
*   **植入位置**：必须埋在 NEMU 所有内存读写的必经之路——`paddr_read()` 和 `paddr_write()`。
*   **性能绞肉机**：`Log` 会触发 I/O，极其缓慢。因此，`mtrace` 必须用 `#ifdef` 包裹，且支持地址范围过滤，绝不可以在跑测试用例时全程开启。
*   **`likely` 宏的魔法**：
    *   代码：`if (likely(in_pmem(addr)))`
    *   底层逻辑：`likely` 是给编译器看的“算命提示”。现代 CPU 流水线遇到 `if` 时，**不等结果算出来，硬件就会预先“瞎猜”**，提前加载下一条指令。加上 `likely`，就是告诉编译器把该分支的代码放在离 CPU 最近的地方，大幅降低流水线冲刷的代价。**它不是“不计算”，而是让硬件更有底气地去“猜”。**

## 模块二：函数追踪（ftrace）与 ELF 文件解析

### 1. ftrace 的核心逻辑
*   **静态解析（查户口）**：启动时打开 ELF 文件，读取符号表（`.symtab`）和字符串表（`.strtab`），建立“地址 -> 函数名”的字典。
*   **动态拦截（抓现行）**：在指令译码阶段（`INSTPAT`），死死盯住 `jal` 和 `jalr` 指令。**如果 `rd == 1`（即 `ra` 寄存器），必为函数调用；如果 `rd == 0 && rs1 == 1`，必为函数返回。** 配合调用深度计数器 `call_depth`，打印出漂亮的缩进日志。

### 2. ELF 文件结构答疑（查户口比喻）
*   **结构套娃**：ELF 像一本书。开头的 `Elf32_Ehdr` 是封面，告诉你目录（`Shdr` 数组）在哪；目录告诉你每个章节（如 `.symtab`）在文件里的具体位置（偏移量）。
*   **字符串切割**：`.symtab` 里存的是定长的结构体（每人 16 字节），而名字全都挤在一起放在了 `.strtab` 的“字符串池”里。结构体里只存一个数字（比如 7），代表去大池子里找第 7 个字符。截取时直接用指针偏移 `strs + st_name` 就可以精准找出来，不需要遍历整个池子。

### 3. 灵魂答疑：栈（Stack）与 `strip`
*   **`ra` 寄存器只有一个，嵌套调用怎么活？** 在真实硬件中，调用函数前，会把当前的 `ra` 存进**内存里的栈（Stack）**中；返回时，再从栈里恢复。寄存器只有一个，但内存很大。
*   **为什么 ftrace 不管栈？** 因为 `ftrace` 只是旁观者，只要看到 `jal` 或 `ret` 就知道发生了跳转，它不需要关心底层栈的物理数据变动。
*   **`strip` 是什么？** 它是一个 Linux 工具，专门用来擦除 ELF 文件里的符号表。擦除后文件体积暴减，但 `ftrace` 就彻底变成了瞎子，只能看到纯机器码。调试期间，**绝对不要 strip 你的程序**。

## 模块三：从软件测试到 DiffTest

### 1. klib 测试与本地验证（native）
*   **控制变量法**：如果 NEMU 里跑 C 代码崩溃，你怎么知道是 NEMU 模拟器有 Bug，还是你的 klib 库写错了？利用 AM 的 `native` 架构，绕过 NEMU，直接在你 Linux 电脑上用 gcc 编译运行。如果 `native` 挂了，说明是你的 C 代码写错了。
*   **三段检查法（Canary）**：测试 `memcpy` 等写入函数时，先填入 `data[i] = i+1` 这种唯一值。断言时，检查 左侧不该被改的、中间被写入的、右侧不该被改的。如果发生越界写（如 `strncpy` 多补了一个 `\0`），Canary 会立刻抓出 Bug。

### 2. 差分测试（DiffTest）的降维打击
*   **核心思想**：找一个绝对权威的标杆（REF，如 Spike）。你的 NEMU（DUT）每执行一条，它就执行一条。只要 PC 或寄存器不一致，立刻报错。
*   **RV32 的正确姿势**：必须选用 RISC-V 官方亲儿子 **Spike**，且在编译时加上 `--enable-m32` 参数，防止 64 位和 32 位高位截断。QEMU 在极端边界情况可能和手册有偏差。
*   **如何比对**：利用 `isa_difftest_checkregs()` 函数，遍历 `x0` 到 `x31`，严格按寄存器编号顺序比对。**为什么不对比内存？** 因为内存太大，每步对比会卡死，寄存器才是核心逻辑。
*   **跳过机制**：遇到 `nemu_trap`（0x6b）这种 REF 根本不认识的自定义指令，必须调用 `difftest_skip_ref()`，让 REF 跳过检查并同步状态。

## 模块四：死循环检测与 Getopt 参数进阶

### 1. 捕捉死循环（Watchdog 机制）
*   **特征码检测**：`while(1);` 编译后的 RISC-V 机器码通常是 `0x0000006f`。在 `execute` 循环里拦截即可。
*   **基于 PC 范围检测**：利用 `iringbuf` 的 16 条记录，找出 `max_pc` 和 `min_pc`。如果极差 `< 16` 字节，说明在这 4 条指令内死转。
*   **防止误杀（冷却计数器）**：正常的 `for` 循环也会在小范围 PC 内跳跃。必须加上计数器（如连续 10 万次都在小范围内），才能判定为死循环。
*   **哨兵法找极值**：找最大值时初始化为 `0`；找最小值时初始化为 `(vaddr_t)-1`（即全 1，无符号数最大）。这保证遍历遇到的第一个真实 PC 一定能成功“踢馆”。

### 2. `getopt_long` 解析参数
*   在 `struct option` 中，第四个字段 `val` 可以填单个字符（如 `'f'`），作为**短选项** `-f`。
*   如果要长选项（如 `--elf`），但不想占用短选项字母，通常填一个大于 255 的**数字**（如 `1000`、`1001`），在 `switch` 里用 `case 1000:` 接收。这不是给用户看的，是给代码做“接头暗号”用的。

## 💡 核心工程素养总结

1.  **防患于未然**：`iringbuf` 的检查要在系统“跑飞”时触发，而不是正常运行时刷屏。
2.  **性能红线**：任何打印（Log/printf）在硬件模拟中都是慢动作。必须用 `#ifdef` 宏和地址过滤，确保关闭时性能零损耗。
3.  **容错与健壮**：读取外部文件（ELF）的 `fread` 返回值必须检查；字符串拷贝必须加溢出保护。NEMU 的编译选项 `-Werror` 是你的好朋友，它会强迫你写出工业级标准的代码。
